# Safecracker — Hack The Box (Sherlock)

**English** | [🇪🇸 Español](README.md)

## Scenario

A user opens a file that looks legitimate and minutes later documents with an odd extension are encrypted. Evidence is the executable, the affected files and host artifacts. The goal is to understand how it encrypts, with which key, and what can be recovered.

## Evidence and triage

```bash
sha256sum *; file *
strings -a -n 8 sample.exe | head -50
```

- **Do not run** the sample outside an isolated, offline VM.
- VirusTotal by hash (not upload) for family context.
- `pefile`/PE-bear for imports, sections and timestamp; `capa` for capabilities.
- Check the encrypted extension and file size: a 16/32-byte difference suggests IV + block.

## Method

1. **Strings and resources**: API names (`CryptEncrypt`, `BCryptEncrypt`), paths, extension and ransom note.
2. **Static analysis**: locate the encryption routine in Ghidra/IDA; identify the algorithm (AES-CBC, XOR, RC4) from constants (`S-box`, `delta`, tables).
3. **Key**: it may be embedded, derived from a password or generated by `CryptGenRandom`. If embedded, extract it from the binary; if random, look in memory or in a key file.
4. **Verification**: decrypt a test file and check the header (`%PDF`, `PK`, `\x89PNG`).
5. **Scope**: count affected files by extension and drive; use `$MFT`/`UsnJrnl` to trace renames.
6. **Disk evidence**: the Sherlock ships a ZIP that is loaded into **Autopsy** (not just the binary). That is where the initial-access account, the encrypted files and the ransom note come from; the case's key question is **which system call deletes the originals** after encrypting them (`NtSetInformationFile` with `FileDispositionInformation`).

## Findings (pattern)

```text
.doc  ->  .doc.<ext>
original size + 16 bytes  ->  16-byte IV + AES-CBC
strings: "README_DECRYPT.txt", "AES", "key"
```

The ransom note and extension confirm ransomware; size aligned to 16 confirms block encryption.

## Lessons

- The PE hash and metadata say more than the file name.
- Correct encryption is not broken: you find the key in the binary, memory or an implementation flaw (same key, fixed IV, XOR).
- The MFT timeline explains what was encrypted and when, even if the binary was deleted.

## Detection and mitigation

- **Sysmon 11** (files created with a new extension) and **1** (process from `%TEMP%`/Downloads).
- Immutable, offline backups; test restoration.
- Block executables from email and enable Windows Defender ASR.
- YARA by family and by encryption routine, not by hash.

MITRE: T1486, T1027, T1059.
